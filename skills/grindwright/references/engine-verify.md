# Verifying game-engine work: one worktree, one editor, real tests

Read this when a lane changes game code in an engine that has an editor (Unity, Godot, Unreal) and "drafted" would otherwise mean "pushed without running". Reading code is not a rung. An unchecked gameplay change in a pull request costs the reviewer a compile error.

## The pattern

1. **Each session gets its own worktree, and an editor opens on that folder.** Engines lock a project folder, not the machine (Unity: `Temp/UnityLockfile`), so separate worktrees can each run their own editor at the same time. Budget about 2 to 4 GB of RAM per open Unity editor, more in play mode, and count the GPU. Two or three at once is a sane default on one desktop. A Personal or Pro licence covers several instances on one machine.
2. **Install the exact editor version the project pins once per machine** (Unity: `ProjectSettings/ProjectVersion.txt`, through `unity install <version> --changeset <hash>`). Never open the project in a newer editor. That upgrades the project and dirties every asset.
3. **Reuse worktrees: keep a warm pool.** The install is shared. The import cache is what each worktree pays for (Unity `Library/`, Godot `.godot/`, Unreal `DerivedDataCache`): minutes and gigabytes on first open. Keep a few long-lived worktrees (`<repo>-pool-1`, `-pool-2`). A session leases one, runs `git switch -c <branch> origin/main` inside it, works, pushes, and hands it back clean (`git status` empty, editor closed). Make a new worktree only when every pooled one is leased. Seed it by copying the import cache from a warm worktree on the same editor version and commit, then let the editor reimport the difference. Record leases in the state folder (`note "lease pool-1" --area resource:pool-1`) so two sessions never share one.
4. **Climb the rungs in order**, cheapest first, and record which ones ran on each ledger item:
   - compile: a batchmode open that fails on `error CS` in the log, or the engine's script check;
   - EditMode or unit tests in batchmode (`Unity -batchmode -nographics -projectPath <wt> -runTests -testPlatform EditMode -testResults <xml> -logFile <log>`; with Unity's CLI, `unity test --mode EditMode`);
   - PlayMode or integration tests in batchmode (`-testPlatform PlayMode`): load the real game scene, build the world in code, step the simulation, and assert on systems and saves;
   - a live editor over the engine's MCP or CLI bridge for what tests cannot see: enter play mode, read the console, take a screenshot, attach it to the pull request. Use this for spot checks, not as the gate.
   Batchmode needs the editor on that worktree closed. Live checks need it open. Do not run both on one worktree at once.
5. **Tests must never touch the player's or owner's real state.** Before the first PlayMode test, find every path a running game writes to (the save file, settings, hint history) and every way it talks to the network (crash reporters, telemetry, bug relays). Point saves at a scratch path through a small seam (an internal override on the save path), and switch the reporters off in the test bootstrap. A direct scene load that "continues the newest save" is a trap: set the loading flag the menu sets, then start a seeded new game yourself.
6. **Determinism first.** Tests need a seeded new game (`NewGame(seed)`), a synchronous tick step (`AdvanceTicks(n)`) instead of the frame timer, and the clock paused, so one seed gives one world. Write a test that two runs of one seed match. Without it, every regression test is a coin flip.
7. **A regression test belongs to its issue and fails on the bug.** Use one class per issue with the issue number as a property, name the expectation, and quote the observed bug in the assertion message. It must compile on both the buggy branch and the fix branch: reach private state by reflection rather than through an API only the fix adds. Show it failing on the branch where the bug lives before you call it a rung. Pair it with a control test (the same setup without the triggering condition) so a test that always fails cannot pass review.
8. **Follow the project's own test plan when it has one.** Look for a testing doc or a Testing section first (`Docs/*`, `CONTRIBUTING`, the agent rules), and build its order, layout and naming rather than inventing your own. If a step changes how the owner works (assembly definitions, CI minutes, branch protection), build it as its own PR and say what changes for them.

## Engine notes

- **Unity assembly definitions.** A test assembly is an asmdef, and an asmdef cannot reference the predefined `Assembly-CSharp`. Game code needs its own asmdef first, and every Editor folder under it needs an Editor-only asmdef. The generated project name changes, so update any compile-check line that names `Assembly-CSharp.csproj`. Serialized type names (`m_TargetAssemblyTypeName: Type, Assembly-CSharp` on UnityEvents, `[SerializeReference]`, Newtonsoft `$type`) name the assembly. Search for them before the split. `m_EditorClassIdentifier` is informational only.
- **Test asmdef essentials (Unity Test Framework).** Set `overrideReferences: true` with `nunit.framework.dll` (plus any precompiled DLL the tests use, such as Newtonsoft), references to `UnityEngine.TestRunner` and `UnityEditor.TestRunner`, and `defineConstraints: ["UNITY_INCLUDE_TESTS"]` so tests never enter a player build. The runtime asmdef gets `InternalsVisibleTo` for both test assemblies.
- **First batchmode run gotchas (each cost a re-run once).** URP 2D types (`Light2D`, `PixelPerfectCamera`) need `Unity.RenderPipelines.Universal.2D.Runtime`, not just the URP runtime. Batchmode has no mouse or keyboard, so game `Update` code reading `Mouse.current` throws, and every PlayMode test fails on the unhandled log; add devices in the test bootstrap (`InputSystem.AddDevice<Mouse>()`, test asmdef references `Unity.InputSystem`) rather than guarding game code. `[Property]` is ambiguous between NUnit and UnityEngine, so write `[NUnit.Framework.Property(...)]`. The first import rewrites some assets (font assets, for example); revert what you did not change before committing.
- **Hosted CI renders nothing.** PlayMode in a container has no display, so assert on state, never pixels. On private repos where CI minutes cost money, run the same commands on a self-hosted runner, or on the machine that holds the warm pool.

## Ledger evidence

An item that changed game code is `drafted` only with this evidence line: `compile ok; EditMode N/N; PlayMode M/M (xml: <path>)`. A rung the lane could not climb is named with its reason (for example `PlayMode: no editor for <version> on this machine`) and counts as a failed check, not a pass.
